# DARK LATTICE WEB DESIGN CONSTITUTION

**Status:** Mandatory  
**Authority:** Project-level design rule  
**Applies to:** Every Dark Lattice website, page, prototype, component, interaction, landing page, product surface, marketing surface, and redesign  
**Primary purpose:** Prevent generic AI-generated, SaaS, startup, luxury-template, and trend-driven web design from entering the product

---

## 0. CLAUDE ENTRY DIRECTIVE

Read this document before proposing, designing, generating, or modifying any web interface for Dark Lattice.

These rules are not preferences. They are acceptance criteria.

If an implementation directly uses a banned pattern, or uses a disguised equivalent, treat the implementation as failed and correct it before presenting it.

Do not defend a violation as:

- subtle
- tasteful
- modern
- expected
- standard practice
- temporary
- only a placeholder
- common in award-winning websites
- necessary for conversion
- acceptable because another brand uses it

When uncertain, choose:

**authored over conventional**  
**structural over decorative**  
**specific over fashionable**  
**evidence over claims**  
**clarity over interface theatre**  
**real behaviour over simulated polish**

---

# 1. DESIGN INTENT

Dark Lattice must not look like a competent version of the current web-design zeitgeist.

The website should feel authored for this company, its games, its systems philosophy, and its evidence. A visitor should not be able to replace the Dark Lattice name with an AI startup, crypto company, design agency, or luxury brand and keep the same interface.

A visually simple page is acceptable.

A template-simple page is not.

The design must earn distinctiveness through:

- composition
- hierarchy
- typography
- scale
- negative space
- real product evidence
- real simulations
- real interaction
- intentional motion
- specific visual language
- meaningful contrast
- disciplined restraint

Decoration must never substitute for a concept.

---

# 2. NON-NEGOTIABLE OUTCOMES

Every Dark Lattice web surface must satisfy all of the following:

1. The design must be identifiable as Dark Lattice without relying only on the logo.
2. Every major visual element must have a functional, informational, narrative, or system-level reason to exist.
3. Claims must be supported by real evidence wherever evidence can reasonably be shown.
4. Interaction must reveal behaviour, information, or state. It must not exist only to make the page feel active.
5. Motion must express causality, transition, scale, hierarchy, or system response.
6. The interface must remain legible and usable without spectacle.
7. Legal, accessibility, privacy, loading, and reduced-motion states must be treated as product requirements.
8. The site must avoid all banned patterns and disguised equivalents defined below.

---

# 3. EQUIVALENCE RULE

A ban applies to the visual idea, not only to the named library or exact implementation.

Examples:

- Replacing Lucide with another generic outline-icon library does not satisfy the icon rule.
- Replacing a purple orb with a cyan orb does not satisfy the orb rule.
- Replacing three feature cards with four feature cards does not satisfy the card rule.
- Replacing a bento grid with an irregular card mosaic does not satisfy the bento rule.
- Replacing liquid glass with another blurred translucent panel does not satisfy the glass rule.
- Replacing Inter with another fashionable startup grotesk does not automatically create an intentional typography system.
- Replacing a fake testimonial with fake logos, fake user counts, unsupported awards, or invented metrics is still fabricated social proof.
- Replacing a soft 20 px radius with a soft 12 px radius is still generic rounded-card design.
- Replacing a CSS gradient with a blurred glowing image used for the same decorative purpose is still a decorative gradient.
- Replacing an animated arrow with a bouncing chevron is still a decorative motion cue.

Do not satisfy the letter of a rule while preserving the same generic visual result.

# 4. BANNED PATTERN REGISTER

## 4.1 Harsh gradients

### Ban

Do not use aggressive CSS gradients as a substitute for composition, material, lighting, or brand identity.

This includes:

- saturated mesh gradients
- neon multi-stop backgrounds
- high-contrast gradient text
- gradient borders
- gradient buttons
- blurred gradient blobs
- animated marketing gradients

### Why

They are one of the most common shortcuts used to make weak layouts feel premium or technological.

### Use instead

- actual lighting
- real imagery
- shader output caused by the system
- tonal contrast
- material response
- controlled single-hue transitions
- negative space
- deliberate surface changes

A physically motivated gradient inside a render, image, simulation, or material is allowed. A generic CSS marketing gradient is not.

---

## 4.2 Lucide icons and generic outline-icon systems

### Ban

Do not use Lucide icons.

Do not replace Lucide with another generic outline-icon library unless a functional interface genuinely requires conventional symbols and no authored alternative is appropriate.

### Why

Generic line icons immediately place the page inside a common SaaS component language.

### Use instead

- text labels
- direct controls
- native symbols
- product-specific glyphs
- custom diagrams
- authored marks
- no icon when the icon adds nothing

---

## 4.3 Pure white backgrounds

### Ban

Do not use pure white as a full-page or major-section background.

### Why

Pure white creates generic presentation-site contrast and conflicts with the Dark Lattice visual identity.

### Use instead

- black
- near-black
- charcoal
- warm off-white for rare document-like surfaces
- material-specific neutral tones

---

## 4.4 Rainbow colouring

### Ban

Do not use rainbow palettes, spectral brand gradients, or multi-hue decoration.

### Why

Rainbow colouring destroys semantic colour discipline and usually exists only to signal creativity or technology.

### Use instead

Use a constrained palette where every accent colour has a defined meaning.

For Dark Lattice:

- resting structure: bone, ash, or restrained cool-white
- deviation: cyan, only when the system deviates
- correction: violet, only when the system suppresses or corrects
- warning or heat: use only where the product semantics require it

---

## 4.5 Drop shadows

### Ban

Do not use generic CSS drop shadows for cards, buttons, panels, or floating interface elements.

### Why

Drop shadows create false depth and generic component separation.

### Use instead

- spacing
- borders
- tonal separation
- occlusion
- scale
- material contrast
- actual 3D depth
- controlled light response

---

## 4.6 Three feature cards in a row

### Ban

Do not present three equal marketing cards in one horizontal row.

Do not change the count while keeping the same generic feature-card logic.

### Why

This is a default SaaS layout, not an authored information structure.

### Use instead

- one strong argument
- a sequence
- a comparison
- a diagram
- a real product demonstration
- asymmetrical editorial composition
- evidence arranged by importance

---

## 4.7 Emojis

### Ban

Do not use emojis as interface decoration, marketing decoration, bullets, labels, or visual shorthand.

### Why

They weaken tone, reduce authorship, and often replace proper visual communication.

### Use instead

- text
- custom marks
- diagrams
- real imagery
- typographic emphasis
- nothing

---

## 4.8 Liquid glass and glassmorphism

### Ban

Do not use:

- blurred translucent panels
- frosted cards
- glass buttons
- liquid-glass navigation
- transparent overlays with decorative blur
- glossy translucent UI shells

### Why

Glassmorphism is a generic surface treatment that often hides weak hierarchy.

### Use instead

- solid surfaces
- direct typography
- real material
- hard transparency only when functionally necessary
- spatial separation
- occlusion
- restrained overlays for readability only

---

## 4.9 Em dashes

### Ban

Do not use em dashes in public-facing Dark Lattice copy.

### Why

The site should use a more controlled sentence rhythm and avoid the common AI-written cadence created by frequent em dashes.

### Use instead

- full stops
- commas
- colons
- parentheses
- shorter sentences
- deliberate line breaks

---

## 4.10 Inter, Geist, and Space Grotesk

### Ban

Do not use:

- Inter
- Geist
- Space Grotesk

Do not replace them with another fashionable default startup sans-serif without an explicit typography decision.

### Why

These fonts strongly signal generic contemporary startup and AI-product design.

### Use instead

Select type based on:

- Dark Lattice identity
- reading role
- display role
- technical role
- tone
- licensing
- performance
- accessibility

The type system must be documented and intentional.

---

## 4.11 Coloured left stripes

### Ban

Do not use coloured left borders as the default visual device for:

- callouts
- quotes
- feature blocks
- alerts
- evidence panels
- headings

### Why

This is a common generated-document and SaaS-dashboard pattern.

### Use instead

- spacing
- rules
- contrast
- indentation
- typography
- numbered structure
- actual semantic components

---

## 4.12 Fake testimonials

### Ban

Do not create, imply, or decorate with fabricated:

- testimonials
- customer quotes
- company logos
- user counts
- ratings
- awards
- investor quotes
- press mentions
- case studies
- metrics
- adoption claims

### Why

Fabricated proof is dishonest and commercially harmful.

### Use instead

- real evidence
- named sources
- product captures
- test results
- public repositories
- verified playtest data
- explicit statements of what is not yet proven

---

## 4.13 Bento grids

### Ban

Do not use bento grids or disguised bento-style mosaics as a default information layout.

### Why

Bento grids have become a generic visual shorthand for modern products and AI-generated landing pages.

### Use instead

- editorial sequencing
- one dominant item with supporting evidence
- linear argument
- project-specific layouts
- diagrams
- full-width demonstrations
- asymmetry based on information importance

---

## 4.14 Decorative terminal windows

### Ban

Do not place content inside a fake terminal window merely to signal technical credibility.

This includes:

- fake command prompts
- fake code logs
- traffic-light window controls
- decorative typing simulations
- invented console output

### Why

Technical credibility should come from real technology and evidence.

### Use instead

- real source excerpts
- real traces
- real telemetry
- actual test output
- diagrams
- measured results
- no terminal treatment when plain text is clearer

---

## 4.15 "It is not X, it is Y"

### Ban

Do not use the copy pattern:

> It is not X, it is Y.

Also avoid close variants that use the same rhetorical structure as a repeated marketing device.

### Why

It is overused in AI-generated brand copy and often creates false contrast.

### Use instead

State what the product is, what it does, and how it can be verified.

---

## 4.16 Checkmark bullets

### Ban

Do not use checkmark bullets for marketing claims, pricing features, or product benefits.

### Why

They reduce complex information to generic sales-list language.

### Use instead

- plain bullets
- numbered steps
- evidence tables
- labelled facts
- diagrams
- prose
- real comparisons

---

## 4.17 Three pricing tiers

### Ban

Do not default to a three-column pricing table.

### Why

It is a standard SaaS conversion template and often produces artificial product segmentation.

### Use instead

Use the pricing structure the product actually requires.

If pricing is not final, do not invent tiers.

If there is one offer, show one offer.

If pricing requires a custom conversation, state that clearly.

---

## 4.18 Claims without real product demonstrations

### Ban

Do not make major capability claims without showing evidence when evidence can reasonably be shown.

### Why

Dark Lattice differentiates itself through systems that behave, not through marketing language.

### Use instead

Show:

- real gameplay
- live simulation
- recorded interaction
- deterministic traces
- before-and-after consequences
- system diagrams
- build captures
- measured performance
- working prototypes

---

## 4.19 Soft generic corner radius

### Ban

Do not use soft rounded rectangles as the default shape for:

- cards
- panels
- buttons
- images
- callouts
- navigation
- forms
- project tiles

### Why

Universal soft corners create generic friendliness and erase material distinction.

### Use instead

- square edges
- hard cuts
- project-specific shapes
- minimal functional radius only where ergonomics, clipping, or native control behaviour genuinely requires it

Default radius should be zero unless documented otherwise.

---

## 4.20 Generic purple-and-black technology aesthetic

### Ban

Do not use purple-and-black as the general brand atmosphere.

### Why

It is a default palette for crypto, AI, gaming, and futuristic product sites.

### Use instead

Dark Lattice may use violet only as a semantic correction colour inside a real system response.

Violet must not become:

- the ambient background glow
- the default button colour
- the brand gradient
- the decorative lighting language
- the generic technology accent

---

## 4.21 Missing loading states

### Ban

Do not ship an experience that has no intentional loading, warm-up, fallback, or failure state.

### Why

A blank canvas, frozen loader, layout jump, or unexplained delay makes the site feel unfinished.

### Use instead

Choose the correct treatment:

- deterministic progress
- staged loader
- skeleton where content structure benefits from it
- static fallback
- reduced-motion fallback
- failure message
- retry path
- progressive enhancement

Do not add a skeleton loader automatically. Use it only when it accurately represents the incoming layout.

---

## 4.22 Decorative radial orbs

### Ban

Do not use glowing radial orbs, blurred spheres, or ambient blob lights as decorative background elements.

### Why

They are a common shortcut for futuristic atmosphere.

### Use instead

A volumetric or particle form is allowed only when it is the actual subject or system, responds meaningfully, and cannot be removed without changing the experience.

A generic glowing orb used as filler is banned.

---

## 4.23 Dot grids

### Ban

Do not use decorative dot-grid backgrounds.

### Why

Dot grids are a generic technology and productivity-site texture.

### Use instead

- empty space
- real diagrams
- structural lines
- product imagery
- material texture
- nothing

---

## 4.24 Sparkle icons

### Ban

Do not use sparkle, magic-wand, stars, or similar "AI magic" iconography.

### Why

They create generic AI-product language and trivialise the technology.

### Use instead

- real system state
- evidence
- custom symbols
- precise labels
- no icon

---

## 4.25 Animated arrows

### Ban

Do not use bouncing arrows, pulsing chevrons, moving pointers, or decorative directional animations.

### Why

They tell the visitor how to use a conventional page while adding visual noise.

### Use instead

- composition
- natural scroll affordance
- clear controls
- static directional marks
- no cue when the action is already obvious

---

## 4.26 Missing Terms of Service

### Ban

Do not publish without Terms of Service when the site or product requires them.

### Use instead

Before release, verify the requirement against:

- product function
- account creation
- transactions
- subscriptions
- user-generated content
- jurisdiction
- current legal advice

Legal text must be real, reviewed, and accessible from the site footer or the correct product surface.

---

## 4.27 Missing Privacy Policy

### Ban

Do not publish without a Privacy Policy when personal data, analytics, cookies, forms, accounts, telemetry, or third-party processors are involved.

### Use instead

Document actual data handling.

Do not copy a generic privacy policy that describes systems the company does not use.

---

## 4.28 Generic hover animations

### Ban

Do not add hover motion as decoration.

This includes:

- card lift
- translateY
- scale-up
- generic glow
- gradient shift
- border animation
- icon wiggle
- arrow motion
- arbitrary blur
- opacity pulse

### Allowed exception

Pointer response is allowed when it is part of real product or system behaviour.

Examples:

- a simulation reacting physically to presence
- a 3D object responding to force
- a timeline exposing state
- a real control showing its active condition
- an information layer becoming available

The response must reveal meaning, state, or causality.

---

## 4.29 Neon colours

### Ban

Do not use neon palettes as ambient styling.

### Why

Neon colours create generic gaming, cyberpunk, crypto, and AI aesthetics.

### Use instead

High-energy colour may appear only when a real event earns it.

For example:

- cyan during deviation
- violet during correction
- heat colour during actual heat or damage
- warning colour during actual warning state

At rest, the site should remain restrained.

---

## 4.30 Basic pastel colours

### Ban

Do not use generic pastel palettes for friendliness, accessibility theatre, or startup warmth.

### Why

Pastels create a soft, interchangeable product tone that conflicts with Dark Lattice.

### Use instead

- neutral materials
- restrained semantic accents
- deep tones
- bone
- ash
- charcoal
- controlled off-white
- project-specific colour where the subject requires it

# 5. MOTION AND INTERACTION CONSTITUTION

## 5.1 Motion must have a reason

Every animation must perform at least one of these functions:

- explain causality
- show state change
- express scale
- preserve spatial continuity
- direct attention
- reveal information
- demonstrate a product capability
- connect user input to system response
- communicate loading or progress

If an animation performs none of these functions, remove it.

## 5.2 Motion must not repair weak composition

Do not use animation to make a static frame feel more sophisticated.

The static composition must already work.

## 5.3 Avoid constant ambient activity

Continuous motion should be rare and restrained.

The interface must not feel like every element is trying to prove that it is alive.

## 5.4 Respect reduced motion

Every meaningful motion sequence needs a reduced-motion interpretation that preserves:

- content
- state
- navigation
- evidence
- comprehension

Reduced motion must not become a broken or empty version of the site.

## 5.5 Scroll must earn its length

Do not consume multiple viewports for:

- a minor zoom
- a simple fade
- a small translation
- a single line of text
- an effect that could happen in one screen

Long scroll sections must deliver a perceptual or informational transformation worth the time.

---

# 6. TYPOGRAPHY CONSTITUTION

Typography is a primary visual system, not a final styling layer.

## Requirements

- Define display, reading, technical, and interface roles.
- Use no more type families than the design can justify.
- Avoid fashionable startup defaults.
- Preserve readable line length.
- Use size and spacing before decoration.
- Avoid excessive uppercase body copy.
- Avoid tiny technical labels used only to create a futuristic atmosphere.
- Do not use tracking as a substitute for hierarchy.
- Do not use monospace everywhere to signal engineering.
- Do not place large display type over the main visual subject unless the overlap is deliberate and preserves both.

## Review question

Would the page still feel authored if all motion and imagery were temporarily removed?

If not, the typography and composition are not carrying enough of the design.

---

# 7. COLOUR AND MATERIAL CONSTITUTION

## 7.1 Every colour needs a role

A colour must represent at least one of:

- identity
- hierarchy
- state
- material
- warning
- interaction
- evidence
- project-specific content

Do not add colour simply because a section feels empty.

## 7.2 Semantic colours remain semantic

Do not spend event colours on ordinary interface decoration.

If cyan means deviation, cyan must not also be the default hover colour.

If violet means correction, violet must not also be the ambient brand glow.

## 7.3 Black is not missing content

Dark negative space may carry:

- scale
- tension
- focus
- transition
- silence
- separation

Do not fill black space automatically.

## 7.4 Material must be structural

Depth should come from:

- geometry
- occlusion
- lighting
- surface response
- scale
- perspective
- real imagery

Avoid fake material effects added only through CSS decoration.

---

# 8. LAYOUT CONSTITUTION

Do not begin with a standard SaaS page recipe.

The following sequence is banned as a default:

Hero  
Logo strip  
Three features  
Bento grid  
Testimonials  
Three pricing tiers  
FAQ  
CTA

Structure the page around:

- the visitor's actual question
- the company's actual evidence
- the product's real state
- the projects being shown
- the information hierarchy
- the necessary action

## Preferred layout behaviours

- editorial sequence
- asymmetry based on importance
- full-width evidence
- one dominant visual argument
- clear project differentiation
- strong pacing
- deliberate section transitions
- no repeated card system unless the information genuinely belongs in a repeated structure

---

# 9. PRODUCT EVIDENCE CONSTITUTION

Never describe a capability where showing it would be more convincing.

If Dark Lattice says a system:

- reacts
- propagates
- remembers
- simulates
- persists
- produces consequences
- behaves deterministically
- creates emergent situations
- accumulates capability
- generates reusable tools

prefer showing:

- a live demonstration
- a real capture
- a trace
- a state diff
- a causal diagram
- a test
- a benchmark
- a repository
- a build
- a before-and-after outcome
- a documented limitation

Evidence must distinguish:

- proven now
- implemented but not externally validated
- planned
- speculative
- historical
- retired

Do not present ambition as current capability.

Avoid:

- reimagine
- revolutionise
- unlock
- supercharge
- seamless
- game-changing
- next-generation
- cutting-edge
- future of
- where X meets Y
- built for the future
- powerful, intuitive, scalable
- transform your
- elevate your
- magic
- effortless
- visionary
- disruptive

Do not use empty claims of innovation.

## 10.2 No invented proof

Never invent:

- statistics
- users
- traction
- revenue
- clients
- partnerships
- awards
- reviews
- quotes
- waitlist numbers
- benchmarks

## 10.3 Prefer concrete language

State:

- what exists
- what it does
- how it works
- what the visitor can see
- what is unfinished
- what is deliberately excluded
- what can be verified

## 10.4 Sentence discipline

- No em dashes.
- Avoid long AI-style contrast constructions.
- Avoid unnecessary rhetorical questions.
- Avoid stacking abstract nouns.
- Prefer short declarative sentences where precision improves.
- Do not explain an effect immediately after the visitor has already understood it.

# 11. ACCESSIBILITY, LOADING, FAILURE, AND LEGAL STATES

These are not cleanup tasks.

They are part of the design.

Every production page must define:

- keyboard navigation
- visible focus
- screen-reader labels
- reduced-motion behaviour
- colour contrast
- text scaling
- mobile interaction
- loading state
- no-JavaScript fallback where relevant
- WebGL failure state where relevant
- empty state
- error state
- retry behaviour
- Terms of Service where required
- Privacy Policy where required
- cookie or consent handling where required
- contact and company information
- legal ownership and attribution for assets

Do not hide broken behaviour behind a visual fallback that makes unsupported claims.

# 12. IMPLEMENTATION PROTOCOL

## 12.1 Before implementation

The agent must write a short decision frame containing:

1. The purpose of the page or component.
2. The visitor's primary task.
3. The information or behaviour that must be demonstrated.
4. The visual mechanism.
5. The banned patterns most likely to appear.
6. The evidence required for acceptance.

## 12.2 During implementation

The agent must:

- preserve the existing design constitution
- reuse existing systems where appropriate
- avoid importing generic component libraries for convenience
- avoid temporary banned styling
- document any intentional exception
- keep real content visible during development
- validate desktop and mobile
- validate reduced motion
- validate loading and failure paths
- validate the static frame before adding motion

## 12.3 Before presenting work

The agent must run the complete audit in Section 13.

Do not present a design that is already known to fail.

---

# 13. DESIGN REVIEW GATE

A design cannot be presented as complete until every gate passes.

## Gate A: Banned-pattern audit

Check all 30 banned patterns.

For each one, record:

- PASS
- NOT APPLICABLE
- FAIL
- EXCEPTION APPROVED

Any unexplained FAIL blocks approval.

## Gate B: Disguised-equivalent audit

Ask:

1. Did I replace a banned pattern with a visual equivalent?
2. Does this still resemble a common AI, SaaS, crypto, luxury, or agency template?
3. Is any major element present only because modern websites usually include it?
4. Did I use effects to hide weak information architecture?
5. Did I use generic motion as polish?
6. Did I choose a trendy font or palette without a project-specific reason?

## Gate C: Evidence audit

Ask:

1. Are all claims supported?
2. Can a major claim be shown rather than stated?
3. Are limitations visible?
4. Are historical and active work clearly separated?
5. Is any ambition written as if it already exists?

## Gate D: Interaction audit

Ask:

1. Does interaction reveal behaviour, state, or information?
2. Is the interaction usable with touch, keyboard, and reduced motion?
3. Does scroll length match the value delivered?
4. Is any animation purely decorative?
5. Does the experience remain coherent without motion?

## Gate E: Production audit

Check:

- desktop
- tablet
- mobile
- keyboard
- screen reader
- reduced motion
- slow network
- WebGL failure
- JavaScript failure where relevant
- loading
- empty state
- error state
- legal links
- privacy handling
- performance
- console
- broken anchors
- dead DOM hooks
- content overflow
- typography loading
- asset licensing

# 14. DESIGN SCORECARD

Score each category from 0 to 2.

## Specificity

- 0: Could belong to any startup.
- 1: Some Dark Lattice-specific content.
- 2: Form and behaviour are inseparable from Dark Lattice.

## Evidence

- 0: Mostly claims.
- 1: Some real proof.
- 2: Major claims are demonstrated or sourced.

## Composition

- 0: Template layout.
- 1: Competent hierarchy.
- 2: Deliberate authored composition.

## Restraint

- 0: Effects compensate for weakness.
- 1: Mostly controlled.
- 2: Every effect earns its place.

## Interaction

- 0: Decorative.
- 1: Functional.
- 2: Reveals system behaviour or meaning.

## Legibility

- 0: Atmosphere obstructs understanding.
- 1: Usable.
- 2: Clear, accessible, and intentional across states.

## Required result

A design needs:

- no automatic failure
- no unresolved banned-pattern violation
- at least 10 out of 12
- a score of 2 in Specificity
- a score of at least 1 in Evidence
- a score of at least 1 in Legibility

---

# 15. AUTOMATIC FAILURE CONDITIONS

Reject the design immediately if any of these are true:

- It resembles a generic AI or SaaS landing page.
- The brand could be replaced without changing the design.
- A banned pattern is used as a major visual device.
- The page relies on unsupported claims.
- The main product capability is described but not demonstrated.
- Motion exists mainly to make the page feel premium.
- The hero consumes substantial scroll without delivering substantial transformation.
- Mobile loses the central interaction or meaning.
- Reduced motion becomes an empty or broken version.
- Legal or privacy requirements are ignored.
- The static frame is weak and motion is being used to rescue it.
- The agent knows the design violates this constitution but presents it anyway.

---

# 16. EXCEPTION PROCESS

An exception is allowed only when all of the following are documented:

1. The exact rule being overridden.
2. The product or accessibility reason.
3. Why a non-banned alternative is worse.
4. The narrow scope of the exception.
5. How the exception avoids becoming a reusable precedent.
6. Jacob's explicit approval.

An exception cannot be inferred from silence.

Previous use of a banned pattern does not approve future use.

---

# 17. AGENT RESPONSE RULES

When proposing design work, Claude must:

- identify the concept in plain language
- state why it belongs to Dark Lattice
- state how it will be built
- state which banned patterns were considered
- state what real evidence appears
- state the mobile and reduced-motion interpretation
- state the kill criterion
- avoid producing multiple large directions when one is required
- avoid generating imagery before the concept is concrete
- avoid defending generic patterns as industry standard

When reviewing existing work, Claude must:

- describe what is actually visible
- separate structural defects from cosmetic defects
- avoid moving the goalposts after implementation
- preserve approved work unless a specific failure is demonstrated
- recommend the smallest change that addresses the proven failure
- clearly label any proposed direction change
- never silently convert a tuning task into a redesign

---

# 18. PRIORITY AND CONFLICT RULE

If this constitution conflicts with:

- a component library
- a template
- an AI recommendation
- a reference website
- a generated design
- a previous implementation
- a trend
- a convenience shortcut
- a default framework style

this constitution wins.

Do not gradually reintroduce banned patterns during later polish.

Do not rationalise a generic result because the implementation is technically sophisticated.

The final standard is simple:

> A finished Dark Lattice website must look authored for Dark Lattice, demonstrate what Dark Lattice can prove, and reject the visual language of generic AI-generated web design.
